# ADR-001: Technology Stack and Key Technical Decisions

**Project:** Hostel Management System (HMS), Team 3, Class 5-J, PES University
**Status:** Accepted
**Date:** 18 Oct 2026 (written in the Dry Run sprint)
**Decision owner:** Harsh M (Technical Lead)
**Related:** Issue HMS-30 (GitHub issue #37), docs/SAD.md (3.a.3, 3.a.5, 3.b.6), docs/DEVIATIONS.md (D-01, D-09, D-11), docs/API_CONTRACT.md

---

## 1. Context

The submitted SRS v1.0 and SAD v1.0 describe a relational database. The course requires the MERN stack, and the professor approved MongoDB with Mongoose in place of the relational database. This is a deviation from the submitted documents and is logged as D-01 in docs/DEVIATIONS.md.

The frontend and backend are built in parallel, so the team needs one written record of the technology choices and the reasons for them. This record covers the stack, authentication, passwords, reports, notifications and the test tools.

## 2. Decisions

The Status column shows whether a choice is already present in the repository or is a design that later stories will implement.

| # | Area | Decision | Reason | Status |
|---|---|---|---|---|
| 1 | Stack | MERN: React (built with Vite) for the frontend, Node.js with Express for the REST API, MongoDB for storage. | The course requires MERN. One language and JSON from browser to database matches the SRS requirement for REST with JSON. | In the repository |
| 2 | Database access | MongoDB accessed through Mongoose. | Approved by the professor. Mongoose schemas and indexes give the validation and uniqueness rules that a relational database would have enforced with constraints. | In the repository |
| 3 | Authentication | Server-side sessions with `express-session` and a MongoDB session store. The cookie is HttpOnly and SameSite=Lax, and the session is rolling with a 30 minute inactivity timeout. | The SRS needs a 30 minute inactivity timeout. Every request renews the session, and the server can end it immediately on logout. No token is kept in browser storage. | Planned, not yet implemented |
| 4 | Login identifier | One field named `identifier` accepts a USN or an email. | A single field is simpler for users. See D-09. | Planned, not yet implemented |
| 5 | Password storage | Passwords are hashed with bcrypt (cost factor 10 or higher). | Meets NFR-002.a. bcrypt is slow by design, which makes guessing attacks expensive. The cost factor will be tuned against the page-load target and checked in the performance tests. | Planned, not yet implemented |
| 6 | Report export | CSV is written by a small renderer in the application. PDF is produced with `pdfkit`. | FR-005.5 needs CSV and PDF. `pdfkit` runs inside Node, so no browser or external service is needed on the server. | Planned, not yet implemented |
| 7 | Email notification | Nodemailer sends the due-date email through the `SMTP_*` settings. A test inbox (Ethereal or Mailtrap) is used in testing. | Notification is an optional feature (FR-003.3). Nodemailer works with any SMTP provider. With no SMTP settings the feature is off and the API returns 503. | Planned, not yet implemented |
| 8 | Scheduled job | `node-cron` runs the fee due-date job once a day inside the Express process. The same job can be run on demand through `POST /api/admin/notifications/run`. | The job is small, so it needs no separate scheduler or service. | Planned, not yet implemented |
| 9 | Backend tests | Node's built-in test runner (`node --test`) with Supertest for API calls. | The backend `test` script and the `supertest` dependency are already in backend/package.json. The runner ships with Node (the project requires Node 20 or later), so no extra test framework is needed. Supertest calls the Express app without a separately started server. Jest is not used. | In the repository |
| 10 | Frontend tests | Vitest (`vitest run`). | The `vitest` dependency and the `test` script are already in frontend/package.json. Vitest works with Vite, the frontend build tool. At the time of writing the frontend has one placeholder test. | In the repository |
| 11 | Code checks and CI | ESLint in both packages, and a GitHub Actions workflow that runs on pull requests to `main`. | Every pull request is checked the same way. D-11 records the two CI checks as required status checks on `main`. | In the repository |
| 12 | Load testing | Not selected yet. The SAD and Test Plan name k6 or autocannon as candidates for NFR-04, and neither is installed in the repository. | The tool will be chosen when the NFR-04 test is prepared. This ADR will then be updated. | Not decided |

## 3. Status of the libraries

Not every library above is installed yet. At the time of writing the backend dependencies are `cors`, `dotenv`, `express` and `mongoose`. The backend development tools are ESLint, Supertest and nodemon. `express-session` with its session store, bcrypt, `pdfkit`, Nodemailer and `node-cron` are added by the stories that use them.

## 4. Alternatives considered

| Option | Why it was not chosen |
|---|---|
| Relational database (SRS v1.0) | The course requires MERN, and the professor approved MongoDB. |
| Token-based login (for example JWT) | The server could not end a session immediately, and a token would have to be kept in the browser. Sessions fit the 30 minute inactivity rule better. |
| Jest for backend tests | It adds a dependency, and Node's built-in runner already covers the need. |

## 5. Consequences

- The design does not depend on foreign keys or CHECK constraints. Integrity is enforced with unique and partial unique indexes, atomic conditional updates and compensating steps where needed (SAD 3.b.5.1).
- The design does not require multi-document transactions. If an operation is later found to need one, it will be recorded in this file and in docs/SAD.md.
- The submitted documents and this stack differ. Each difference is listed in docs/DEVIATIONS.md.
- The frontend must send requests with credentials included, because the session travels in a cookie.
- Secrets (`SESSION_SECRET`, `MONGODB_URI`, SMTP credentials) come from environment variables, and `.env` is never committed.
- The 200 concurrent user target is not claimed as met until a load test has been run and the result recorded.

## 6. Changing this decision

A change to any row above is made in a new pull request that updates this file and, where it applies, docs/SAD.md and docs/DEVIATIONS.md. The change is announced to the team in the group chat.
